## 4. 历史清理方案（尚未执行，需明确批准）

规范第 5 节禁止在未经明确批准的情况下 Force Push、重写历史或移动 Tag。以下为可选方案与代价，**当前均未执行**。

### 方案 A — 不重写历史，仅记录（当前状态）

- **操作**：保持现状，本文件作为长期记录
- **结果**：历史中残留该文件名；源码不再新增暴露
- **代价**：无；不破坏任何已有提交、Tag 或发布记录
- **适用**：信息敏感度低（本事件属此类）

### 方案 B — 重写历史并强制推送

- **操作**：`git filter-repo` 替换历史中的字符串，然后 Force Push 受影响分支
- **代价与风险**：
  - 违反「未经批准不得 Force Push」，需逐分支明确授权
  - `v0.1.0-beta` 指向的提交内容会改变，**必须重建 Tag**，破坏既有发布记录的不可变性
  - 所有克隆、Fork、PR 引用与 CI 运行记录将失效或指向失效对象
  - GitHub 会保留不可达对象一段时间，且已 Fork 的副本无法回收
  - 无法保证第三方镜像或缓存副本被清除
- **评估**：**不建议**。本事件不含凭据，重写历史的破坏性远大于残留风险

### 方案 C — 凭据类问题的标准处置（本事件不适用）

若暴露的是真实凭据，应：立即撤销并轮换密钥 → 审计使用记录 → 评估影响 → 再考虑历史处理。本次未涉及凭据，故不适用。
