# 公开信息治理与隐私保护规范

本文件规定 ExamPilot 在公开交付中的信息分级、审查范围与推送前门禁。适用于所有开发、审查、测试、提交、推送、合并及发布任务。

**基本原则：内部研发信息默认不公开；对外发布遵循最小必要披露。** 公开交付以产品、技术实现、可验证的测试结果和正式维护记录为核心，不将私人工作过程复制为公开文档或 Git 历史。

---

## 1. 信息分级

### PUBLIC — 允许公开

- 产品功能、架构与技术设计
- 正式源代码、必要测试及契约
- 可复现的测试方法与真实验证结果
- 用户文档、技术文档及 Release Notes
- 软件版本、兼容性与已知限制
- 必要的许可证、第三方声明及正式作者署名
- 经过确认可以公开的安全与维护信息

### INTERNAL — 默认不得公开

- 内部工具、协作方式与工作流程
- 任务分工、内部沟通记录与私人偏好
- 内部协作记录与专用验收日志
- 本地用户名、电脑名称、磁盘绝对路径
- 私有仓库名称、内部工作区及非公开链接
- 内部截图、调试日志、实验记录和临时目录
- 无公开必要的个人身份及环境信息

上述内容可以保存在授权的内部记录中，但不得未经审查进入公开仓库。

### SECRET — 禁止提交和传播

- API Key、Token、密码和凭据
- 私钥、会话令牌、敏感环境变量
- 真实用户数据库、个人文件及备份
- 未授权公开的个人数据或第三方机密

敏感值不得进入 Git、日志、PR、Issue、CI Artifacts 或 Release。

---

## 2. 公开内容写作规范

公开文字必须使用专业、中立、客观的工程表述，不无必要地披露内部工具或协作方式。

| 避免 | 推荐 |
| --- | --- |
| 「某工具/某人已完成代码」 | `Implemented and verified` |
| 「某验收工具宣布 PASS」 | `Regression tests passed` |
| 「用某模型修复了该问题」 | 描述缺陷现象、根因与修复方式 |
| 无依据的 `independently validated` | 仅在**确有独立验收证据**时使用，并注明证据来源 |
| 泛泛的「已通过测试」 | 写明命令、范围与结果，如 `CI passed on commit <sha>` |

不得通过删除工具名称而伪造验收事实，不得把开发者自验包装为独立验收。

产品实际依赖的 AI SDK、Provider 协议、合法第三方依赖及必须保留的许可证信息，不属于应隐藏的内部开发记录。

---

## 3. 审查范围

公开信息审查必须覆盖：

- README、文档、代码注释和测试数据
- Git Commit 标题与正文
- Branch 名称
- Pull Request 标题、描述与评论
- Issue、Discussion 及审查记录
- Changelog、版本标签与 Release Notes
- 截图、附件、构建产物和 CI Artifacts
- 配置文件、元数据和文件名

不得只检查源代码而忽略托管平台页面上公开的文字和附件。

---

## 4. 推送前门禁

任何公开交付之前必须完成：

1. 确认目标仓库及公开范围
2. 检查新增、修改和拟提交的文件
3. 检查 Commit Message、PR 描述及 Release Notes
4. 扫描敏感凭据、私人路径、个人信息和内部开发记录
5. 移除无必要的内部信息，保留正确的技术事实
6. 确认许可证、正式署名和必要的来源声明完整
7. 确认测试、CI 与版本状态真实且对应正确提交

发现隐私风险或敏感信息时，应先停止相关公开操作，完成审查后再继续。不得为赶进度跳过此门禁。

### 自动化检查

```bash
npm run check:public-info
```

该脚本扫描全部受版本控制的文件与提交信息，检查凭据特征、本地绝对路径、个人信息与内部记录。**自动化检查只能发现已知模式，不能替代人工审查。**

`npm run check:public-info` 已纳入 CI，任何一项命中都会使构建失败。

---

## 5. 已公开信息的处理

如果发现信息已经进入公开仓库：

1. 首先确认信息类型、影响范围与严重程度
2. 对当前源码和文档进行安全修正
3. 对可编辑的公开 PR、Issue 和说明进行必要整改
4. 如涉及真实凭据，立即报告并制定撤销、轮换与补救方案
5. 检查历史 Commit、Tag、Release 和公开附件中的残留
6. **不得声称普通新提交能够清除历史信息**
7. 未经用户明确批准，不得 Force Push、重写历史、移动 Tag 或破坏已有发布记录

对于无法通过正常方式清除的历史信息，应准确报告残留及风险，由用户决定后续处理方式。参见 [history-exposure-report.md](history-exposure-report.md)。

---

## 6. 内部与公开仓库隔离

当项目同时存在内部仓库和公开仓库时：

- 内部仓库可以保留必要的研发、协作和决策证据
- 公开仓库只接收审查通过的正式交付内容
- 不得直接将内部仓库历史、文档和私有文件整体推送到公开仓库
- 公开交付应采用经过审查的文件范围和正常 Git 流程

本项目特别约定：**完整课程题库、原始 PDF 及其派生文件永不进入公开仓库**，公开仓库只包含自行编写的示例题库。详见 [CONTRIBUTING.md](../CONTRIBUTING.md)。

---

## 7. 验收标准

只有满足以下条件，才能报告 `PUBLIC_READY`：

- [ ] 公开内容不包含未经批准的私人或内部信息
- [ ] 未发现未处理的敏感凭据泄露
- [ ] Commit、PR、文档及发布说明均经过审查
- [ ] 工程验证结果准确、可追溯
- [ ] 许可证和必要公开信息完整
- [ ] 已知历史暴露问题得到明确记录和处理决定

**`PUBLIC_READY` 不等于仓库历史中的一切信息已被永久消除。**

任何未确认项目必须标记为未验证，不得猜测或默认安全。

---

## 8. 执行权限

本规范允许进行检查，但**不构成** Commit、Push、Tag、Release 或历史修改的授权。这些操作仍须遵守项目既有授权与数据安全规则。

如本规范与其他项目指令存在冲突，优先保护数据安全和用户隐私，并在发布前明确报告冲突。
